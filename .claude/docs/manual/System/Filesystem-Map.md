and a **proposed** cleaner target — so a future tidy-up is deliberate, not guesswork.

> runs day-to-day. Folders are **not** renamed casually — several are referenced by hardcoded
> paths and would break integrations. This is a reference + plan, not a set of applied changes.

## 3. The file-storage model (where documents live)

- **Generated PDFs we produce and persist:** signed contracts → `data/contracts/{signed,student}/`;
  partner certs → `storage/partner-certs/`.
- **LoAs / visa letters / attendance letters are NOT stored as files** — they're **generated on
  demand** from the DB record ("living document" behaviour: auto-resync, same QR, no reissue).
  That's why there's no big LoA file store to find.
- **Inbound uploads** all under `uploads/<category>/`.
- **Secrets** currently sit **loose in the SIS root** (see §4) — the one genuinely fragile spot.

## 6. Proposed target hierarchy (NOT applied — the plan)

The whole tree resolves to **four file buckets, one rule each**:

| Bucket | Rule | Holds |
|---|---|---|
| `public/` | internet can fetch it | UI pages, images, fonts, shareable media (`launch/`, `app-guide/` if public) |
| `uploads/` | came **from a user** | student docs, certs, screenshots, vetting |
| `data/` | **we generated / own** it | contracts, certs, catalog, app-guide, json |
| `.secrets/` | credentials, server-only | zoho/xero/google tokens (moved out of root) |

**Open design choice (Neil):** keep `uploads/` (inbound) and `data/` (generated) as **siblings**
[preserves *provenance* — user-uploaded vs system-generated, which drives retention/privacy], **or**
nest both under a single `storage/` parent (`storage/uploads/`, `storage/generated/`). Both are
valid; the sibling model is the current de-facto shape and needs less rewiring.

**Concrete first steps toward it (low-risk, in order):**
1. ✅ `app-guide-*` → `data/app-guide/` (done; pipeline repointed).
2. Fold `storage/partner-certs/` → `data/certs/` + update `partner-cert.ts:26` `CACHE_DIR`; delete empty `storage/`. *(cache dir — regenerates; very low risk.)*
3. Sweep the orphaned `payload-*`/`diag_*` junk + the `.bak` files (§5).
4. **Deliberate:** move the 3 token/key files → `.secrets/` and update the 3–4 hardcoded refs in one commit + verify. *(fixes the real fragility.)*

## 7. Migration risk notes

- Anything referenced by **hardcoded `path.join(__dirname, '..', '..', …)`** breaks on move unless
  the ref is updated in the same change (tokens, `data/contracts`, `uploads/*`, `storage/partner-certs`).
- **Cron** paths are absolute in the crontab — moving `dist/` or `catalog-sync.sh` means editing crontab too.
- `dist/` is regenerated by `npm run build`; never move/edit it directly.
- Always `grep -rn "<oldpath>"` before any move; update refs; rebuild; verify.
